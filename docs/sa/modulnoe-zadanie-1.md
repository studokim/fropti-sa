# Модульное задание 1

В рамках задания вам нужно придумать сложную систему, реализовать ее API и задокументировать. Это будет ваш проект.

#### Идеи для сервиса

Откуда можно брать идеи для сервиса:

* Доработать проект одного из курсов прошлого года (UCD, архитектура, управление проектами) ИЛИ проект по одному из курсов по выбору текущего года (рек.системы, дэшборды, тексты)

  * проект должен иметь новое ветвление в своем развитии (новый сервис/интеграцию, пользовательский флоу, техническую реализацию и тд) -- просто взять и описать as-is завершенный проект или проект с соседнего курса нельзя

* Выбрать одну из предложенных систем (но не более 3 команд на один вариант системы)

  * Сервис для управления задачами и проектами

  * Сайт для бронирования жилья

  * Мобильное приложения для заказа и доставки еды

  * Платформа для онлайн-обучения (LMS)

  * Мобильное приложение сети медицинских клиник

  * Сервис для коллективной работы над документами

  * Сайт интернет магазина

**Требования** базового варианта проекта:

1. Представлена концепция системы, которая включает:

   1. не менее 3 юзер сторей (user stories) для описания основной функциональности системы

   2. схему архитектуры системы в любой из изученных в рамках магистратуры нотаций

2. Создан свой API с не менее чем 5 запросами (эндпоинтами) всего и как минимум 2 различными HTTP-методами (например, GET и POST)

   1. API может иметь заглушки

   2. API можно протестировать, прогнав его запросы

3. Система задокументирована по темам этого модуля, документация содержит

   1. Техническое задание на frontend и/или backend с описанием (любое на выбор):

      1. описание алгоритма выполнения обработчика по расписанию

      2. описание интеграции (любого типа) между backend-сервисами (например, структура передаваемого сообщения и обработка сообщения)

      3. описание сущности бд

      4. не менее одной экранных форм и поведения ее элементов, а также клиент-серверного взаимодействия

   2. не менее 3 диаграмм всего

      1. для каждой приведено описание того, зачем она нужна, в каком случае будет полезна, какой это тип диаграммы и какую нотацию / инструмент вы использовали для ее создания

      2. использование не менее 2 различных типов диаграмм

      3. диаграммы не дублируют схему из концепции (двойная сдача одной и той же схемы не допускается)

   3. описание методов API с помощью OpenAPI-спецификации (yaml-файл, Swagger, Speca.io )

   4. не менее 2 сценариев использования (use cases)

      * в каждом присутствует не менее 2 акторов и 6 шагов самого сценария

#### Состав команды

Итоговый отчет по проекту должен быть выполнен в группах 2-4 человека. Базовый вариант, описанный выше – это вариант для 2 участников, при наличии третьего участника проекта к требованиям добавляется

* 2 (два) метода в API и документация к ним

* в API необходимо использовать не менее 3 различных HTTP-методов (например, GET, POST и PATCH)

* 1 сценарий использования

* 1 дополнительная диаграмма

#### Сроки

Проект сдается в ++3 этапа++:

1. **03.10** сдача концепций системы (пункт 1 из требований выше)

2. **17.10** сдача рецензии концепции системы назначенной вам команды (команда на ревью будет известна 05.10), которое включает:

   1. оценку юзер сторей по критериям качества и полноты, связности и способности покрыть основную функциональность

   2. критический разбор архитектурной схемы по оптимальности выбранной нотации, точности отображения компонентов схемы и их взаимодействия, а также соответствия юзер сторям

   3. возможные предложения по улучшению/оптимизации ключевых составляющих системы (например, относительно архитектурных решений, бизнес-логики, пользовательского опыта и тд)

3. **31.10** итоговый отчет, который включает в себя представленную ранее и улучшенную по результатам рецензии концепцию системы, техническую документацию к системе (п. 3 задания), работающий API (код И ссылку на swagger, где можно выполнить запросы, либо коллекцию с запросами)

Предполагаемые разделы итогового отчета:

* техническая документация: диаграммы, ТЗ, сценарии использования

* API-спецификация

* код, ссылки

* рефлексия отличий от предварительного плана, если эти отличия есть

* описание индивидуального вклада
