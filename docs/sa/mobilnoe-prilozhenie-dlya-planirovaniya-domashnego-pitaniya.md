# Мобильное приложение для планирования домашнего питания

Команда: Айзенберг Семён, Муравьёв Кирилл.

## 1. О системе

**Fropti** («fresh & optimal») — мобильное приложение, которое планирует питание за пользователя: автоматически составляет меню из рецептов с учётом продуктов, уже имеющихся дома, ведёт «холодильник» и список покупок, минимизируя остатки и выброшенные продукты. Приложение — offline-first: рецепты, холодильник, меню и сама генерация работают без сети; сервер нужен только для маркетплейса, оплат и обновления каталогов.

Приложение уже было придумано (хотя и не реализовано) ранее. Для модульного задания предлагается развитие: **доставка домашней заморозки**.

В занятые дни пользователь может не готовить, а заказать готовое замороженное блюдо домашней кухни (не полуфабрикат — блюдо полностью приготовлено и требует только разогрева) у повара-исполнителя из своего района. Собственной логистики платформа не содержит: доставку выполняет сторонний подрядчик (например, Яндекс.Доставка). Заморозка снимает главное ограничение классической доставки еды — блюдо не нужно есть сразу после приготовления, поэтому недельный набор можно привезти одной доставкой, а работа в пределах одного района делает такую доставку дешёвой даже с учётом комиссии подрядчика.

## 2. Акторы

| Актор             | Роль в системе                                                             |
| ----------------- | -------------------------------------------------------------------------- |
| Пользователь      | Планирует питание, ведёт «холодильник», заказывает домашнюю заморозку      |
| Повар-исполнитель | Сторонний домашний кулинар: публикует блюда, готовит и замораживает заказы |
| Модератор         | Проверяет поваров и блюда, обрабатывает отзывы и инциденты                 |

Курьер не является актором системы: доставка полностью передана внешнему подрядчику и интегрирована через API (раздел 4).

## 3. User Stories

US-1. Автоматическое меню из того, что есть дома

> Как **пользователь**, я хочу **автоматически получать меню на неделю с учётом продуктов, которые уже есть у меня**, чтобы **не тратить время на планирование и выбрасывать меньше продуктов**.

US-2. Делегирование готовки — доставка домашней заморозки

> Как **пользователь**, я хочу **заменить готовку блюда заказом готового замороженного блюда у повара из моего района**, чтобы **в занятые дни есть домашнюю еду, не проводя вечер у плиты**.

US-3. Карточка замороженного блюда

> Как **пользователь**, я хочу **видеть состав, фото, пищевую ценность, цену и отзывы соседей о блюде; наличие медкнижки у повара**, чтобы **быть уверенным в качестве и безопасности еды до оплаты**.

US-4. Публикация блюд поваром

> Как **повар-исполнитель**, я хочу **опубликовать блюда, которые готовлю, с составом, ценой[^price] и числом порций на неделю**, чтобы **получать заказы от соседей и подрабатывать на своей кухне**.

[^price]: Наш сервис ограничивает диапазон возможных цен, поскольку блюда мы включаем в автоматическое меню.

### Ключевые потоки

1. **Генерация меню (офлайн).** Всё происходит на устройстве: встроенный движок строит меню по локальной SQLite-базе (рецепты, холодильник, настройки) и кэшу каталога заморозки района. Сервер не участвует.
2. **Синхронизация (при появлении сети).** Приложение подтягивает через API дельта-обновления каталога рецептов и актуальный каталог заморозки района.
3. **Заказ заморозки.** Приложение оформляет заказ через API -> API создаёт платёж в ЮKassa -> вебхук о платеже превращается в событие `OrderPaid` -> сервис заказов активирует заказ и уведомляет повара.
4. **Исполнение и доставка.** Повар ведёт статусы -> события уходят в очередь -> когда блюдо готово и заморожено, сервис заказов создаёт заявку в Яндекс.Доставке (адреса повара и заказчика, слот) -> вебхуки о статусах доставки приходят в сервис заказов.
5. **Модерация.** Панель модератора работает через общий API: проверка поваров и блюд до публикации, разбор инцидентов.

### Архитектурные решения

- **Offline-first клиента**: SQLite и движок генерации делают планирование полностью автономным; сервер нужен только для каталогов, маркетплейса и оплат. Это соответствует исходному замыслу проекта («базовые функции на устройстве») и устраняет зависимость главной ценности продукта от сети. Движок можно переиспользовать и на сервере (например, для веб-версии).
- **Кэш каталога заморозки района**: каталог мал (блюда поваров одного района), поэтому генератор учитывает «делегирование готовки» даже офлайн (но предупреждает, что данные могут быть неактуальны); заказ можно оформить только онлайн.
- **Единый REST API** — одна точка входа и авторизации (JWT) для двух мобильных приложений и панели модератора.
- **Сервис заказов выделен отдельным контейнером**: у маркетплейса свой домен и жизненный цикл, его можно развивать и масштабировать независимо от API.
- **Доставка передана подрядчику**: платформа не содержит собственной логистики — нет курьеров, маршрутов и слотов, только интеграция «заявка + вебхуки»; это резко сужает scope и операционные риски.
- **Одна PostgreSQL на старте**: в ней только серверные данные (аккаунты, каталоги, заказы); разделение — при росте нагрузки.
- **RabbitMQ** развязывает синхронный API и фоновую обработку, гарантирует доставку событий заказов и платежей.
- **Оплата через платёжный шлюз по вебхукам** — стандартная и безопасная схема, взятая у маркетплейсов.
